# Регламент сбора недостающих данных для анкеты портала ОК (okcom.js)

**Статус:** ПЛАН РАБОТ (подготовка внедрения портала ОК в dmiandr/context)
**Ветка:** qwen-develop
**Основание:** TASK-0304 (узловая) — анкета ОК = клон протокола семи адаптеров
**Правило №0:** ИИ сама не напишет ничего. Анкета заполняется только по фактам, подтверждённым живой разметкой. Нет факта — стоп и вопрос.
**Связанные документы:**
- `docs/OK_ANALYSIS_GAPS.md` — перечень недостающих данных
- `docs/SUMMARY_ANALYSIS_OK.md` — текущее состояние исследования
- `docs/connecting_a_new_portalinstruction.md` — чек-лист ручных проверок F12
- `scripts/InspectOK-DOM.ps1` — образец запросов CDP (архив TASK-0302, служит эталоном структуры 15 секций)

---

## 1. Цель документа

Определить **порядок, критерии и контрольные точки** сбора недостающих данных по порталу ОК, необходимых для заполнения анкеты `okcom.js`. Документ описывает **план работ** (не сам скрипт). Результатом каждого этапа является **подтверждённый факт** о живой разметке ok.ru, который попадает в анкету.

### Принципы
1. **Только факты:** каждая строка селектора в анкете имеет источник (запись из точечной проверки F12 / инспекции CDP).
2. **Портал один, типы страниц разные:** данные собираются по каждому типу страницы отдельно.
3. **Подтверждение перед анкетой:** селектор считается валидным только после проверки на 2–3 живых экземплярах страницы.
4. **Один шаг — один отчёт:** результат каждого прогона фиксируется отдельным файлом (по образцу 15 секций).

> **Граница применимости:** расширение **не используется на мобильных устройствах** — мобильные представления не являются рабочими сценариями и не исследуются. Домен `m.ok.ru` рассматривается **исключительно как запасной источник поиска селекторов** при неудаче поиска на основном домене `ok.ru` (и не входит в список рабочих urls анкеты).

## 2. Структура сбора (эталон — 15 секций InspectOK-DOM.ps1)

Сбор данных ведётся по **15 секциям** — единый формат для всех типов страниц:

| № | Секция | Что фиксируется | Атом анкеты |
|---|--------|-----------------|-------------|
| 01 | PAGE | URL, title, тип страницы, портал | urls / Mark |
| 02 | SELECTED_ENTITY | селектор выбранного элемента, классы, data-атрибуты | zone.element |
| 03 | ENTITY_CANDIDATES | кандидаты идентичности (href, data-*, parent) | username (B4) |
| 04 | EVENT_CONTAINER | контейнер события (комментарий/пост) | eventype, totalblock (B5, B9) |
| 05 | EVENT_TEXT | контейнер текста, исключения тегов | GetEventText (B12) |
| 06 | DATE_TIME | элемент даты, формат, атрибут datetime/time | GetTimestamp (B11) |
| 07 | ROOT_CONTEXT | заголовок диалога/страницы, title-селектор | GetRootFor |
| 08 | COMMENT_URL | пермалинк комментария, якорь | url события (B8) |
| 09 | TRIANGLE_ANCHOR | точка вставки меню (после/до имени) | attachMenuDomElement (B6) |
| 10 | PAGE_BEHAVIOR | SPA/динамическая загрузка/History API | стратегия обновления (A13) |
| 11 | SHADOW_DOM | наличие Shadow DOM | совместимость движка |
| 12 | CONTEXT_MENU | поведение контекстного меню | взаимодействие зоны |
| 13 | RAW_HTML | живой HTML-фрагмент | подтверждение селекторов |
| 14 | SELECTORS | итоговые подтверждённые селекторы | функции анкеты |
| 15 | NOTES | метаданные прогона (дата, профиль, порт) | — |

> Секции, помеченные «failed» в прошлых прогонах (02–14), являются **первоочередной целью** повторного сбора.

## 3. Типы страниц для сбора (приоритеты)

Данные собираются отдельно по каждому типу страницы. Приоритет определён уроками vk/lj (вложенность и пермалинки — главные боли ОК).

| Приоритет | Тип страницы | URL-паттерн | Зачем нужно |
|-----------|--------------|-------------|-------------|
| P0 | Дискуссия / комментарий | `/discussions/…/<topic>/<message>` | пермалинк, eventype=1, комментарии |
| P0 | Профиль | `/profile/NNN`, слаг `имя.число{6,}` | username, упоминание |
| P0 | Группа | `/group/NNN`, `groupNNN`, короткий слаг | eventype=2, посты группы |
| P1 | Ответ на комментарий (вложенный) | `/discussions/…/<topic>/<reply>` | IsNested, testnestedre |
| P1 | Нить личных сообщений (ЛС) | ЛС (нить) | пермалинк ЛС, вложенность |
| P1 | Пост (запись) как событие | пост/лента | eventype=2, captElement |
| P2 | Упоминание автора (вне события) | любая ссылка на автора | бейдж/меню для не-событий |
| P2 | Товар / фото / видео | соответствующие маршруты | дополнительные зоны |

> Рабочий домен сбора — **`ok.ru`** (основной). Домен `m.ok.ru` — только запасной источник поиска селекторов при фиаско на основном домене; мобильных представлений не касается.

## 4. Порядок работ (этапы)

Каждый этап завершается **подтверждённым фактом** и оформляется как отчёт по 15 секциям.

### Этап 1. Восстановление рабочего сбора DOM
- **Цель:** устранить ошибку «Не удалось получить корень DOM» (прошлые прогоны дали только 2 из 15 секций).
- **Действия:**
  1. Проверить `DOM.getDocument` (depth параметры) в headed Edge + CDP.
  2. Подтвердить получение `rootNodeId` до запуска сбора секций.
  3. Зафиксировать рабочую команду получения корня.
- **Контроль:** получение непустого `rootNodeId`; далее секции 02–14 становятся доступными для заполнения.

### Этап 2. Сбор базовых трёх типов страниц (P0)
- **Действия:** по каждому из трёх подтверждённых типов (дискуссия, профиль, группа) провести сбор по 15 секциям.
- **Минимум прогонов:** 2–3 экземпляра каждого типа страницы.
- **Контроль:** для каждого типа получены секции 02, 04, 06, 08, 14 (см. §6).

### Этап 3. Сбор вложенности и пермалинков (P1)
- **Действия:** исследовать ответ на комментарий (IsNested/testnestedre) и нить ЛС (пермалинк).
- **Контроль:** секция 08 (COMMENT_URL) содержит пермалинк; секция 09 — точка вставки меню.

### Этап 4. Дополнительные типы и поведение (P1–P2)
- **Действия:** собрать упоминания, пост, товар/фото; проверить PAGE_BEHAVIOR и SHADOW_DOM.
- **Контроль:** секции 10–11 заполнены по всем исследованным типам.

### Этап 5. Консолидация в анкету okcom.js
- **Действия:** на основе подтверждённых секций заполнить атомы A1–A14 на языке VK-операций.
- **Ворота:** у каждой строки селектора в анкете есть источник (проверка F12 / отчёт).
- **Контроль:** анкета собрана без ручного JS, по правилу №0.

## 5. Образец запросов (эталон из InspectOK-DOM.ps1)

Запросы к странице выполняются через **CDP + WebSocket** (структура — из образца `InspectOK-DOM.ps1`):

| Действие | CDP-метод | Параметры |
|----------|-----------|-----------|
| Включить домены | `Page.enable`, `DOM.enable`, `Runtime.enable` | — |
| Получить корень DOM | `DOM.getDocument` | `depth` |
| Найти узлы по селектору | `DOM.querySelectorAll` | `nodeId`, `selector` |
| Разрешить узел в объект | `DOM.resolveNode` | `nodeId` |
| Получить свойства (innerText) | `Runtime.getProperties` | `objectId` |
| Выполнить JS-выражение | `Runtime.evaluate` | `expression` |

**Образец набора селекторов (по типам страниц, из образца):**

| Сценарий | Стартовые селекторы (гипотезы) |
|----------|--------------------------------|
| `profile_page` | `.card-author`, `.username`, `.profile-header` |
| `group_page` | `.group-title`, `.group-header`, `.community-name` |
| `comments_author` | `div.mediac` (базовый контейнер) |

> ⚠️ Важно: перечисленные селекторы — это **гипотезы из архивного скрипта**, а не подтверждённые факты. Они подлежат **обязательной перепроверке** на живой разметке (правило №0). В анкету попадают только подтверждённые варианты.

## 6. Критерии готовности по секциям

Секция считается собранной, если выполнены все условия:

| Секция | Критерий готовности |
|--------|---------------------|
| 01 PAGE | заполнен всегда (url, title, тип, портал) |
| 02 SELECTED_ENTITY | получен стабильный селектор элемента (не хэш, не nth-child с фрагментами) |
| 03 ENTITY_CANDIDATES | найдены href и/или data-атрибуты идентичности |
| 04 EVENT_CONTAINER | определён контейнер события с маркером (класс/id) |
| 05 EVENT_TEXT | извлечён текст без автора/даты/управления |
| 06 DATE_TIME | найден элемент даты и формат (datetime/text) |
| 07 ROOT_CONTEXT | определён заголовок диалога и title-селектор |
| 08 COMMENT_URL | получен пермалинк комментария (глубокая ссылка) |
| 09 TRIANGLE_ANCHOR | определена точка вставки меню |
| 10 PAGE_BEHAVIOR | определён SPA/статический характер страницы |
| 11 SHADOW_DOM | определён факт наличия/отсутствия Shadow DOM |
| 12 CONTEXT_MENU | описано поведение контекстного меню |
| 13 RAW_HTML | сохранён живой HTML-фрагмент |
| 14 SELECTORS | итоговые селекторы подтверждены на 2–3 страницах |
| 15 NOTES | заполнены метаданные (дата, профиль, порт) |

## 7. Контрольные точки и критерий PASS/FAIL

### Контрольная точка 1 (после Этапа 1)
- ✅ PASS: получен рабочий `rootNodeId`; прогон даёт >2 заполненных секций.
- ❌ FAIL: корень DOM не получен — остановка, диагностика CDP/Edge, повтор.

### Контрольная точка 2 (после Этапов 2–3)
- ✅ PASS: по типам P0 и P1 собраны секции 02, 04, 06, 08, 09, 14.
- ❌ FAIL: селекторы не подтверждаются на 2–3 страницах — стоп, уточнить.

### ��онтрольная точка 3 (после Этапа 5)
- ✅ PASS: анкета `okcom.js` собрана, каждая строка селектора имеет источник.
- ❌ FAIL: есть селекторы без источника — анкета не принимается.

**Правило фриза (из записки):** три и более правки одной задачи подряд, уход от узловой задачи, усталость архитектора — СТОП и новый диалог с запиской.

## 8. Форматы фиксации результатов

1. **Отчёт по 15 секциям** — для каждого прогона (JSON по образцу `InspectOK-DOM.ps1`), путь `docs/dom-inspection/`.
2. **Сводный документ** — обновление `SUMMARY_ANALYSIS_OK.md` после каждого этапа.
3. **Журнал пробелов** — обновление `OK_ANALYSIS_GAPS.md`: закрытые пункты помечаются как собранные.

## 9. Риски и ограничения

| Риск | Митигирование |
|------|---------------|
| Headless блокируется антиботом ОК | использовать только headed Edge + CDP (порты 9224/9226) |
| Селекторы из архива — гипотезы | обязательная перепроверка на 2–3 живых страницах |
| SPA/динамическая загрузка (если подтвердится) | MutationObserver / пересканирование по истории |
| Нестабильные хэшированные классы | предпочитать href-шаблоны и data-атрибуты (урок vk) |
| Отсутствие данных по новым типам страниц | приоритет P0 → P1 → P2, не блокируя узловую задачу |
| Фиаско поиска селекторов на основном домене | допустим запасной поиск по `m.ok.ru` (без мобильных представлений) |

## 10. Заключение

Регламент определяет план сбора недостающих данных для анкеты ОК: восстановление рабочего сбора DOM (Этап 1), сбор трёх базовых типов страниц (Этап 2), вложенности и пермалинков (Этап 3), дополнительных типов и поведения (Этап 4), консолидацию в анкету (Этап 5). Каждый факт проходит контрольные точки и попадает в анкету только с источником (правило №0).

Расширение работает на десктопных браузерах на основном домене `ok.ru`; мобильные представления не используются. Домен `m.ok.ru` — только запасной источник поиска селекторов при неудаче на основном домене.
