# Регламент сбора недостающих данных для анкеты портала ОК (okcom.js) — версия v01

**Статус:** ПЛАН РАБОТ (подготовка внедрения портала ОК в dmiandr/context)
**Ветка:** qwen-develop
**Основание:** TASK-0304 (узловая) — анкета ОК = клон протокола семи адаптеров
**Версия исследования:** v01 (ручной протокол на базе DevTools/F12)
**Правило №0:** ИИ сама не напишет ничего. Анкета заполняется только по фактам, подтверждённым живой разметкой. Нет факта — стоп и вопрос.
**Граница применимости:** расширение работает на десктопных браузерах на основном домене `ok.ru`; мобильные представления не используются. Домен `m.ok.ru` — только запасной источник поиска селекторов при неудаче на основном домене.

**Принцип исследования (основа):** ручной протокол из `connecting_a_new_portalinstruction.md` — исследование через **DevTools Edge (F12)**, без автоматизации обстрела портала. Человек выбирает элемент вручную, библиотека отвечает на вопросы «что спросить у страницы», результат фиксируется стандартизированным отчётом.

---

## 1. Цель документа

Определить **порядок, критерии и контрольные точки** сбора недостающих данных по порталу ОК вручную (через F12) для заполнения анкеты `okcom.js`. Результат каждого шага — **подтверждённый факт** о живой разметке ok.ru, который попадает в анкету.

### Принципы (наследуются из `connecting_a_new_portalinstruction.md`)
1. **Только ручная проверка живого элемента.** Без автоматических «обстрелов» портала: движок потребляет селекторы анкеты, а не массовые запросы.
2. **Только факты.** Каждая строка селектора имеет источник — запись из конкретной точечной проверки F12.
3. **Элемент выбирает человек.** Оператор ПКМ → «Проверить» → `$0` указывает на выбранный элемент (имя автора и т.п.).
4. **Проверка на 2–3 экземплярах** каждого типа страницы перед фиксацией.
5. **Один шаг — один отчёт.** Результат фиксируется стандартизированным файлом.

---

## 2. Инструменты и требования (из `connecting_a_new_portalinstruction.md`)

- Браузер: **Microsoft Edge** (только).
- Инструмент: **DevTools Edge (F12)**, вкладки **Elements** и **Console**.
- Никаких сторонних расширений.
- Никакого обязательного знания JavaScript/DOM/CSS от оператора.

### Ручной поток работы
1. Открыть ok.ru → перейти на нужный тип страницы.
2. Навести ПКМ на элемент (имя автора / заголовок / дата) → **«Проверить»** — элемент подсвечивается в Elements и доступен как `$0`.
3. В Console выполнить точечные функции (см. §4) — получить селектор, контейнер, дату и т.д.
4. Зафиксировать результат в стандартизированный отчёт (см. §5).

---

## 3. Типы страниц и приоритеты сбора

Данные собираются вручную по каждому типу страницы отдельно. Приоритет — уроки vk/lj (вложенность и пермалинки — главные боли ОК).

| Приоритет | Тип страницы | URL-паттерн | Цель сбора |
|-----------|--------------|-------------|------------|
| P0 | Дискуссия / комментарий | `/discussions/…/<topic>/<message>` | пермалинк, eventype=1 |
| P0 | Профиль | `/profile/NNN`, слаг `имя.число{6,}` | username, упоминание |
| P0 | Группа | `/group/NNN`, `groupNNN`, короткий слаг | eventype=2, посты группы |
| P1 | Ответ на комментарий (вложенный) | `/discussions/…/<topic>/<reply>` | IsNested, testnestedre |
| P1 | Нить ЛС | нить личных сообщений | пермалинк ЛС, вложенность |
| P1 | Пост (запись) как событие | пост/лента | eventype=2, captElement |
| P2 | Упоминание автора (вне события) | любая ссылка на автора | бейдж/меню |
| P2 | Товар / фото / видео | соответствующие маршруты | дополнительные зоны |

## 4. Точечные функции (ручной протокол — «что спросить у страницы»)

Для выбранного элемента `$0` выполняются функции библиотеки (образец — JS-библиотека из `connecting_a_new_portalinstruction.md`):

| Функция | Что возвращает | Какая секция/атом |
|---------|----------------|-------------------|
| `getSelector($0)` | CSS-путь до элемента | 02 SELECTED_ENTITY / zone.element |
| `findEntityCandidates($0)` | кандидаты идентичности (href, data-*, parent) | 03 ENTITY_CANDIDATES / username |
| `findEventContainer($0)` | контейнер события | 04 EVENT_CONTAINER / eventype, totalblock |
| `extractMessageText($0)` | текст события | 05 EVENT_TEXT / GetEventText |
| `extractDate($0)` | дату и её селектор | 06 DATE_TIME / GetTimestamp |
| `findConversationContext($0)` | заголовок диалога/страницы | 07 ROOT_CONTEXT / GetRootFor |
| `findTriangleAnchor($0)` | точки вставки меню | 09 TRIANGLE_ANCHOR / attachMenuDomElement |
| `inspectPageBehavior()` | SPA/динамику/History API | 10 PAGE_BEHAVIOR / стратегия |
| `inspectShadowRoot($0)` | наличие Shadow DOM | 11 SHADOW_DOM |
| `inspectPage()` | сводную информацию о странице | 01 PAGE / обзор |
| `saveInspection("NAME")` | сохранить отчёт в TXT | весь отчёт 01–15 |

## 5. Формат фиксации (стандартизированный отчёт)

Каждый собранный файл оформляется по 15 секциям (структура из `connecting_a_new_portalinstruction.md`):

```
[01] PAGE            — URL, hostname, title
[02] SELECTED_ENTITY — tag, id, class, selector, text, attributes
[03] ENTITY_CANDIDATES — href / data-* / parent ссылки
[04] EVENT_CONTAINER — selector, reason, depth
[05] EVENT_TEXT      — текст события
[06] DATE_TIME       — текст/атрибут даты
[07] ROOT_CONTEXT    — заголовок диалога, url
[08] COMMENT_URL     — пермалинк комментария
[09] TRIANGLE_ANCHOR — точки вставки меню
[10] PAGE_BEHAVIOR   — SPA/History/динамика
[11] SHADOW_DOM      — факт наличия
[12] CONTEXT_MENU    — ручная проверка
[13] RAW_HTML        — живой HTML фрагмент
[14] SELECTORS       — итоговые селекторы
[15] NOTES           — метаданные
```

> Именование файлов по образцу: `OK_<тип страницы>_<№>.txt` (например, `OK_discussion_01.txt`). В NITROUTES фиксируются: дата, профиль, порт, версия, источник (F12).

## 6. Порядок работ (этапы) — ручной протокол

### Этап 1. Подготовка среды
- Открыть Microsoft Edge, войти в ok.ru, открыть headed-профиль (порты 9224/9226 при необходимости).
- Убедиться, что DevTools F12 открывается и `$0` работает.
- **Контроль:** `inspectSelectedElement()` на тестовом элементе возвращает отчёт.

### Этап 2. Сбор трёх базовых типов страниц (P0)
- По каждому типу (дискуссия, профиль, группа): 2–3 экземпляра.
- Для каждого: ПКМ на имени автора → «Проверить» → выполнить функции §4 → сохранить отчёт.
- **Контроль:** получены секции 02, 04, 06, 08, 09, 14 по всем трём типам.

### Этап 3. Сбор вложенности и пермалинков (P1)
- Ответ на комментарий (IsNested/testnestedre) и нить ЛС (пермалинк).
- **Контроль:** секция 08 содержит пермалинк; секция 09 — точку вставки меню.

### Этап 4. Дополнительные типы и поведение (P1–P2)
- Упоминания, пост, товар/фото; проверить PAGE_BEHAVIOR и SHADOW_DOM.
- **Контроль:** секции 10–11 заполнены.

### Этап 5. Консолидация в анкету okcom.js
- Заполнить атомы A1–A14 на языке VK-операций по подтверждённым фактам.
- **Ворота:** у каждой строки селектора есть источник (отчёт F12).
- **Контроль:** анкета собрана без ручного JS (правило №0).

## 7. Критерии готовности по секциям

| Секция | Критерий готовности |
|--------|---------------------|
| 02 SELECTED_ENTITY | стабильный селектор (не хэш, не nth-child с фрагментами) |
| 03 ENTITY_CANDIDATES | найдены href и/или data-атрибуты |
| 04 EVENT_CONTAINER | контейнер события с маркером |
| 06 DATE_TIME | найден элемент даты и формат |
| 08 COMMENT_URL | пермалинк комментария (глубокая ссылка) |
| 09 TRIANGLE_ANCHOR | точка вставки меню |
| 14 SELECTORS | селекторы подтверждены на 2–3 страницах |

---

## 8. Контрольные точки и PASS/FAIL

### КТ-1 (после Этапа 2)
- ✅ PASS: по типам P0 собраны секции 02, 04, 06, 08, 09, 14.
- ❌ FAIL: селекторы не подтверждаются на 2–3 страницах — стоп, уточнить (допустим запасной поиск по `m.ok.ru`).

### КТ-2 (после Этапа 5)
- ✅ PASS: анкета `okcom.js` собрана, каждая строка селектора имеет источник.
- ❌ FAIL: есть селекторы без источника — анкета не принимается.

**Правило фриза:** три и более правки одной задачи подряд, уход от узловой задачи, усталость архитектора — СТОП и новый диалог с запиской.

---

## 9. Форматы фиксации результатов

1. **Отчёт по 15 секциям** — для каждого прогона (TXT по образцу `connecting_a_new_portalinstruction.md`).
2. **Сводный документ** — обновление `SUMMARY_ANALYSIS_OK.md` после каждого этапа.
3. **Журнал пробелов** — обновление `OK_ANALYSIS_GAPS.md`: закрытые пункты помечаются как собранные.

## 10. Риски и ограничения

| Риск | Митигирование |
|------|---------------|
| Headless блокируется антиботом ОК | только headed Edge + CDP, ручной F12 |
| Селекторы — гипотезы | обязательная перепроверка на 2–3 живых страницах |
| SPA/динамическая загрузка (если подтвердится) | MutationObserver / пересканирование |
| Нестабильные хэшированные классы | предпочитать href-шаблоны и data-атрибуты (урок vk) |
| Отсутствие данных по новым типам страниц | приоритет P0 → P1 → P2 |

## 11. Заключение

Регламент определяет **ручной порядок** сбора недостающих данных для анкеты ОК на основе DevTools/F12 (принцип из `connecting_a_new_portalinstruction.md`): подготовка среды, сбор трёх базовых типов страниц, вложенности и пермалинков, дополнительных типов и поведения, консолидация в анкету. Каждый факт проходит контрольные точки и попадает в анкету только с источником (правило №0).

**Следующий шаг:** Этап 1 (подготовка среды) и ручной сбор по типам P0.
